Critical - Routing Foundation
Case Type + Case Reason are the two most important fields in the entire system
These are the only fields the routing engine queries on. They narrow the pool from all 10 templates down to 1–2 candidates. If either field is missing or set incorrectly, the CMT returns nothing - and the draft fails entirely.

Once the candidates are returned, a second step takes over: the AI reads the When To Use guidance on each candidate to make the final selection between first-contact and follow-up variants.
Step 1 - Routing Gate
Case Type + Case Reason determine which templates are even in play. Get these wrong and nothing works. This is the most critical data quality requirement for your CSR team.
Step 2 - Final Selection
When To Use (on the CMT record) is what the AI reads to choose between two templates that share the same Type + Reason. If the AI picks the wrong variant, sharpen this text - no code change needed.

How it works
Thread-aware replies - what is actually happening
The LLM does not "know" the email thread on its own. Thread awareness is the result of two components working together.
Step 1 - Prompt Flow
Data retrieval - the Flow puts the thread into the prompt
The Add_Historical_Case_Emails_to_Prompt2 Prompt Flow runs at runtime. It queries the EmailMessage records linked to the case and assembles the full email thread as a block of text. That text is injected into the prompt payload before it reaches Einstein. The LLM never fetches the thread itself - the Flow puts it there.
Step 2 - Prompt Template
LLM instructions - the template tells Einstein what to do with the thread
The Custom_CSR_Reply Prompt Template includes explicit instructions telling Einstein to read the thread context it has been given, understand what was already communicated to the provider, answer the provider's specific questions, and avoid repeating information already sent.
In plain terms: The Prompt Flow is responsible for fetching and injecting the email thread. The Prompt Template is responsible for instructing the LLM to read and respond to it. Remove either one and the thread-awareness breaks. Without the Flow, the LLM sees no thread. Without the right Template instructions, the LLM ignores it or handles it incorrectly.

Step-by-step: from case to draft
Every step that runs when a CSR clicks "Draft with AI" - what triggers it, what it reads, what it produces.
Step 1 - Salesforce Case
CSR opens a case and clicks "Draft with AI"
The case has a Case Type and Case Reason - set by intake or the CSR. These two fields are the only routing keys the entire system depends on.

Case Type Case Reason Case Description Email Thread (Activity)
Step 2 - GenAI Prompt Template
CSR selects "CSR First Contact Email" or "CSR Reply Email"
Two GenAI Prompt Templates are available from the Draft with AI menu. The CSR picks based on whether this is a new enquiry or an ongoing thread.

Custom_CSR_Response - First Contact Custom_CSR_Reply - Reply

Each template immediately invokes the Prompt Flow to assemble context before the AI writes anything.
Prompt Flow invoked automatically
Step 3 - Prompt Flow
Add Historical Case Emails to Prompt2 - assembles the full AI prompt
The flow does two jobs:

1. Email history - loops the Activity timeline and appends all prior emails so the AI has full thread context.

2. Template candidates - queries Template_Scenario__mdt where Case Type and Reason match. For each match, it reads Email_Template_API_Name__c and fetches the body from EmailTemplate. Template name, When_To_Use guidance, and body are appended to the prompt.
CMT query: Case_Type__c = X AND Case_Reason__c = Y
Step 4 - Custom Metadata Type (Routing Index)
Template_Scenario__mdt - the phone book that maps every case to the right template
The Phone Book Analogy
Think of Template_Scenario__mdt as a phone book. The case gives you a name (Case Type + Case Reason), and the phone book gives you the number to call (the email template developer name). Without it, you'd search through all 1,600 contacts every time. With it, you look up the name and get the answer instantly.
Why Custom Metadata - not a custom object, custom setting, or hardcoded logic
✓ Deployable across environments - CMT records travel with metadata deployments (sandbox → production). Custom object records don't. Routing rules never need to be manually recreated in each environment.
✓ Queryable in Flows - no custom code - The Prompt Flow queries it at runtime with a simple lookup: give me the row where Case Type = X and Case Reason = Y. No Apex, no developer needed.
✓ Admin-editable, no code required - Your content team adds, changes, or removes routing rules in Setup without a developer. New case scenario? Add a row. Template changed? Update the developer name. Done.
✓ No governor limit concerns - CMT queries don't count against SOQL limits. This matters at scale when the system is generating drafts across hundreds of cases per day.
✓ Version-controlled and auditable - Every change is trackable through metadata deployments. You always know who changed which routing rule and when.
Why store the Email Template Developer Name - not the Id
→Developer names are stable across environments - the same template has the same developer name in sandbox and production, but different Ids. Storing the Id would break routing rules every time you migrate.
→Developer names are human-readable - an admin sees Credentialing_Medical_Director_Change and immediately knows what it is. An Id like 00Xf4000001abc tells them nothing.
Why the When_To_Use__c field
This is the instruction label for Einstein AI - a plain-English description like "Use this template when the provider is following up on a Medical Director Change request where the document checklist has already been sent." It serves two purposes:

1.Helps Einstein disambiguate when multiple templates share the same Case Type + Reason 2.Acts as documentation for admins - they can read the field and understand when each routing rule fires without needing to open the template
One-sentence pitch: Custom Metadata gives us a routing index that's deployable, queryable, admin-owned, and free from governor limits - it's the Salesforce-native way to map business rules to actions without code.

EmailTemplate lookup: WHERE DeveloperName = pointer
Step 5 - EmailTemplate (Body Source)
Flow fetches the full template body at runtime
The EmailTemplate.Body field holds the complete policy-accurate text - form references, SLA numbers, compliance language, insurance minimums.

Why here? Content teams edit template language in Setup → Email Templates - a familiar no-code UI. Changes are instant with no deployment required.

10 EmailTemplates - 6 credentialing + 4 patient journey
Full context assembled → sent to Einstein AI
Step 6 - Einstein AI (LLM)
AI selects the best-fit template and writes the personalised draft
The AI receives one prompt containing: case description + fields · prior email thread · all candidate templates with When_To_Use guidance · full EmailTemplate body for each candidate.

It reads the When_To_Use text to select the most appropriate template, uses the body as the structural backbone, and layers in case-specific details - names, dates, license numbers, product lot numbers - from the case description and thread.
Step 7 - Output
Draft appears in the Email composer - CSR reviews and sends
The draft is pre-populated in the Salesforce Email composer. The selected template name appears at the top. The CSR can edit, revise, or regenerate before sending. Nothing is sent automatically.

Architecture Change
Before vs After
The template body moved out of Custom Metadata and into native Email Templates - separating the platform layer (IT-managed) from the content layer (business-managed).
Before - Body stored in CMT
Where the body livedTemplate_Body__c field on each CMT record - a long text area baked into metadata.
How to update languageSetup → Custom Metadata Types → manage records → edit textarea. Deploy if in a sandbox. Not intuitive for a content team.
Who can edit itSalesforce admin or SA only - requires metadata deployment access. Content teams could not edit in production without a release.
Flow behaviourFlow read {!CurrentTemplate.Template_Body__c} directly - body was frozen in deployed metadata.
Adding a new scenarioCreate CMT record, paste body into Template_Body__c, deploy. Body tied to the metadata lifecycle.
After - Body stored in EmailTemplate
Where the body livesEmailTemplate.Body in the Allergan Demo Templates folder - native Salesforce Email Templates.
How to update languageSetup → Email Templates → open template → edit body. Rich text, no deployment, immediate effect. Content teams own this.
Who can edit itAny user with Manage Public Classic Email Templates - no admin or deployment access needed for edits.
Flow behaviourFlow reads Email_Template_API_Name__c from CMT then does a live lookup: EmailTemplate WHERE DeveloperName = [pointer]. Body is always the current live version.
Adding a new scenarioCreate EmailTemplate → create CMT record pointing to it. Two tools, cleaner ownership split. No code, no Flow deployment.

Frequently Asked Questions
Common questions about how the system works
Real questions asked during discovery and testing - answered plainly.
Is Case Type + Reason the most important attribute to pick the right email template?

Yes - with one important nuance. Case Type + Reason is the routing gate. It is the only thing the system queries on. It narrows the pool from all templates down to 1–2 candidates. If either field is missing or wrong, the CMT returns nothing and the draft fails entirely.

But there is a second step. Once the candidates are returned, the AI reads the When To Use field on each candidate to make the final selection - for example, choosing between a first-contact and a follow-up variant that share the same Type + Reason.

Step 1 - Routing GateCase Type + Case Reason narrow the candidate pool. Wrong values = draft fails.
Step 2 - Final PickWhen_To_Use__c is what the AI reads to choose between candidates. Tune this text if the AI picks the wrong variant.
So with Case Type and Reason, does the system go and directly query the email templates and pick one?

No - there is an intentional middle layer. The system does not query EmailTemplates directly from the case. It goes through the CMT routing index first.

Case Type + Reason
↓
Query CMT (not EmailTemplates)
↓
CMT returns a pointer: Email_Template_API_Name__c
↓
Flow looks up EmailTemplate WHERE DeveloperName = [pointer]
↓
Gets the template body → passes to Einstein AI

The CMT is a pure routing index - it does not store template content. It just holds the address (pointer) to the right EmailTemplate. This separation means routing rules and template content can be managed independently.

When picking the right template, does the system look at the header or subject line of the email template?

No. The subject line and display name are irrelevant to selection. The system matches on the DeveloperName field - the API name set when the template was created in Setup.

The CMT record stores the DeveloperName in Email_Template_API_Name__c. The Flow queries EmailTemplate WHERE DeveloperName = [that value]. Out of thousands of templates in the org, it goes directly to the one matching record - the other templates are never touched.

Think of it as a barcodeThe CMT record holds the barcode number. The Flow scans for it. Subject line, folder, display name - none of these matter. Only the DeveloperName barcode matches.
CriticalThe DeveloperName in the CMT must match the EmailTemplate DeveloperName exactly - case-sensitive, no spaces. A mismatch returns nothing silently.
What exactly does the system look at in the CMT to determine which template to use - is it the When To Use, Case Reason, or Case Type field?

All three fields are used - but at different stages and for different purposes.

Case_Type__c + Case_Reason__cUsed by the Flow to query the CMT. Exact string match - narrows the full CMT to 1–2 candidates. No AI involved here.
When_To_Use__cUsed by Einstein AI to choose between candidates when two records share the same Type + Reason. The AI reads this text and decides which fits the context.
Email_Template_API_Name__cThe pointer used by the Flow to fetch the EmailTemplate body once the right candidate is identified.

In short: Case Type + Reason find the candidates. When To Use picks between them. The API Name fetches the content.

Say I have one case "Upcoming Leave" - how does the system find the right email template out of 1,600 templates in the org?

The system never searches through all 1,600 templates. The CMT record acts as a direct address - it already knows the exact DeveloperName to look up. Here is the step-by-step using that example:

1
Flow reads the case: Case Type = "HR", Case Reason = "Upcoming Leave"
2
Flow queries CMT: WHERE Case_Type__c = "HR" AND Case_Reason__c = "Upcoming Leave" → returns 1 record
3
Flow reads the pointer: Email_Template_API_Name__c = "Employee_Leave"
4
Flow queries EmailTemplates: WHERE DeveloperName = "Employee_Leave" → returns exactly 1 template. The other 1,599 are never touched.
5
Flow passes the body to Einstein → draft is written using that template as the structure.
What if I have two templates - "Employee Leave" and "Contractor Leave" - how does the system know which one to pick?

You create two CMT records - both with the same Case Type and Case Reason, but each pointing to a different EmailTemplate and with different When_To_Use guidance.

1
Flow queries CMT: WHERE Case_Type__c = "HR" AND Case_Reason__c = "Upcoming Leave" → returns both records
2
Flow fetches both template bodies and passes them to Einstein along with their When_To_Use text:
Template 1: Employee_Leave - "Use when contact is a full-time employee"
Template 2: Contractor_Leave - "Use when contact is a contractor or vendor"
3
Einstein reads the case description (e.g. "John Smith, contractor from Accenture") and the two When_To_Use instructions → picks Contractor_Leave
4
Draft is written using the Contractor_Leave body as the structure.
Case Type + ReasonTells the system which pool to look in - returns both candidates.
Case description + When_To_UseTells the AI which one to pick from that pool. The distinction between Employee vs Contractor is never hardcoded - it lives purely in the When_To_Use text you write.
When_To_Use__c seems like a very important field - who actually reads it to determine which email template to use?

Einstein AI reads it - not the Flow, not any Salesforce logic or automation.

The Flow's job is purely mechanical. It queries the CMT, fetches the template bodies, and assembles everything into one big prompt. It passes When_To_Use__c to Einstein as text, but it does not act on it or make any decision based on it.

Einstein is the one that reads When_To_Use__c and makes the judgment call. Here is what Einstein receives:

Template 1: Employee_Leave
When to use: "Use when contact is a full-time employee"
Body: [full employee leave template text]
+
Template 2: Contractor_Leave
When to use: "Use when contact is a contractor or vendor"
Body: [full contractor leave template text]
+
Case description: "John Smith, contractor from Accenture..."
↓
Einstein reads all of this → picks Contractor_Leave
Einstein owns this decisionIf the AI keeps picking the wrong template, the fix is not in the Flow or any code - it is in the When_To_Use__c text on the CMT record. That text is literally the instruction you are giving Einstein. Make it more specific and Einstein will make a better decision.
Think of it this wayWhen_To_Use__c is plain-English instructions written to Einstein. The better you write it, the more accurately Einstein picks the right template every time.
What happens if the CSR selects the wrong prompt template - for example, uses "CSR First Contact Email" on a reply case, or "CSR Reply Email" on a brand new case?

The system will not error or stop - it will still generate a draft. But the tone and structure will be wrong for the situation.

Wrong choice 1CSR First Contact Email used on a reply case. The draft will be written as if this is the first time the provider is being contacted. It will repeat the full document checklist and requirements the provider already received. The provider will feel ignored - like no one read their previous email.
Wrong choice 2CSR Reply Email used on a brand new case. The draft will try to reference a prior email thread that does not exist. It may produce a vague or incomplete response because it has no thread context to work from - and it will skip the full policy structure and checklist the provider needs on first contact.

The routing - Case Type, Case Reason, CMT, EmailTemplate - works correctly regardless of which prompt template the CSR picks. The difference between the two is purely about context and tone:

CSR First Contact EmailTells Einstein: "This is a new case. No prior thread exists. Draft a complete opening email with the full checklist."
CSR Reply EmailTells Einstein: "A thread already exists. Read it, address what the provider asked, and do not repeat what was already sent."

The CSR is the control point here. The descriptions in the Draft with AI menu make it clear which to use - the system cannot auto-detect whether a case is new or ongoing, so the CSR has to make that judgment call before clicking Generate.

Best practice for CSRs Before clicking Draft with AI - check the Emails section on the case. If there are no prior emails, use First Contact. If there is already an email thread, use Reply. Two seconds of checking saves a draft that has to be completely rewritten.
