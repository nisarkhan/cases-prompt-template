How It Works — Architecture Deep-Dive

Use this section to explain the technical architecture to Rohit and Shankar. It covers what you built, where the intelligence lives, and why it is designed the way it is.

The two moving parts

1. GenAI Prompt Template
The instruction set for the LLM. Contains the live Case merge fields, all three candidate email templates embedded as text, the selection rules, and the guardrails. This is what you (Nisar) own and maintain.

File: Custom_CSR_Response.genAiPromptTemplate-meta.xml
Type: einstein_gpt__caseEmailDraft — this type activates the native "Draft with AI" button automatically. No LWC needed to trigger it.
2. Prompt Flow
A standard Salesforce Flow that runs before the LLM generates. It queries closed historical cases with the same Case Type and Reason, reads the outbound email bodies from those cases, and injects them into the Prompt Template as grounding context.

File: Add_Historical_Case_Emails_to_Prompt2.flow-meta.xml
This flow was not modified for this demo — it was already built.

Inside the Prompt Template — 4 sections

The template has four clearly separated sections. Each section has a specific job. When the CSR clicks Generate, these four sections are assembled in sequence and sent to the LLM as a single prompt.

Section 1 — CURRENT CASE   (the signal)
Injects live Case data using Salesforce merge fields at runtime. The LLM reads Type, Reason, Subject, and Description to understand what kind of case it is dealing with. The merge fields resolve to real values before the LLM sees the prompt.
### CURRENT CASE Case Number: {!$Input:Case.CaseNumber} Type: {!$Input:Case.Type} Reason: {!$Input:Case.Reason} Description: {!$Input:Case.Description} Customer: {!$Input:Case.Contact.FirstName} {!$Input:Case.Contact.LastName} Account: {!$Input:Case.Account.Name} CSR Name: {!$Input:Sender.FirstName} {!$Input:Sender.LastName}
What to say to the customer: "The purple tokens are Salesforce merge fields. They resolve to real values at runtime — the LLM never sees {!$Input:Case.Type}, it sees 'Account Support'. This is standard Salesforce merge field syntax, nothing custom."
Section 2 — CANDIDATE EMAIL TEMPLATES   (the selection logic)
All three email templates are embedded directly in the prompt. Each has a Use when: condition that tells the LLM when to pick it. The LLM pattern-matches the Case Description against these three conditions and selects one. This is the entire template selection mechanism — no rules engine, no code, no Flow logic.
### CANDIDATE EMAIL TEMPLATES Choose the single most appropriate template based on Case Type, Reason, and Description. After selecting, use it as your structural foundation — fill in all placeholders with real case values. Do NOT remove, reorder, or paraphrase any mandatory language, form names, or legal statements. TEMPLATE A: Credentialing - Medical Director Change Request Use when: Case involves a request to change or update the Medical Director on a credentialed account. --- [full email body — Form AM-CMD-001, 5–7 business days, placeholders] TEMPLATE B: Credentialing - New Practice Enrollment Use when: Case involves a new practice or facility requesting to enroll as an Allergan Moxie provider. --- [full email body — Forms AM-PE-002 + AM-PC-005, 10–14 business days] TEMPLATE C: Product Support - Not Eligible for Products Use when: Case involves a provider being informed they do not meet eligibility requirements. --- [full email body — Form AM-EL-010, 30-day dispute window]
This is the key design decision. Rather than asking the LLM to write an email from scratch — which risks hallucinating form numbers or SLAs — we give it the pre-approved templates as structure. The LLM's job is to pick the right one and fill the placeholders. It cannot rewrite the mandatory language. Think of it as: the template is the rails, the LLM is the engine that personalises the journey.
Section 3 — HISTORICAL CONTEXT   (the tone calibration)
A single merge field that expands at runtime to the outbound email bodies of up to three previously closed cases with the same Type and Reason. The Prompt Flow queries these records and produces this text before the LLM generates. The LLM uses the examples to calibrate tone — it learns how your experienced reps write, not from generic training data.
### HISTORICAL CONTEXT The following are real outbound responses from similar closed cases. Use these to calibrate tone and solution steps — but always use the selected template above as your structure: {!$Flow:Add_Historical_Case_Emails_to_Prompt2.Prompt}
What to say to the customer: "This one token expands to the actual email text your experienced reps wrote on similar closed cases. The AI learns your team's tone from real examples. In the production version, as your team closes more cases, the grounding pool improves automatically."
Section 4 — INSTRUCTIONS   (the guardrails)
Explicit rules the LLM must follow. These are the compliance guardrails that make the output auditable and prevent the most common failure modes.
### INSTRUCTIONS 1. State which template you selected on line 1: "Selected template: [Template A / B / C]" 2. Then output the complete email body — fill every [placeholder] with real values from the Case Details above. 3. Do NOT invent form names, case numbers, or contact details. Use only what is provided. 4. Do NOT remove any form names (e.g. AM-CMD-001), legal statements, or processing time commitments from the template. 5. Adjust the tone to be warm and professional. 6. End with the CSR's real name from the Case Details above.
Rule 1 makes selection auditable — you can always see which template was chosen. Rule 3 and 4 are the compliance guardrails — the AI is explicitly forbidden from inventing or removing form references and SLAs. Rule 6 ensures the CSR's actual name appears in the sign-off, not a generic placeholder.

Why embed templates in the prompt instead of querying EmailTemplate records?

Rohit may ask why the templates are baked into the prompt text rather than queried dynamically from Salesforce's EmailTemplate object. This is a deliberate Phase 1 decision.

ApproachHow it worksWhen to use
Embedded (current demo) All candidate templates are inside the prompt text. The LLM picks from what it can read directly. Proof of concept and demos. Fast to build, easy to test and tune. Works until the candidate set grows beyond ~5–7 templates.
Query and inject (Phase 2) A Prompt Flow queries EmailTemplate records, filters to the top N candidates based on Case Type/Reason tags, then injects only those into the prompt. Production with many templates. Requires EmailTemplate records to be tagged with metadata (Type, Reason, Category). This is Rohit's team's build.
LLM picks by name (Phase 3) The LLM sees only template names and use-case descriptions (not full bodies), selects a name, then a second step fetches and fills the chosen template. Scale to thousands of templates. Requires a two-step prompt chain. Future roadmap.

How the type activates the native "Draft with AI" button

The Prompt Template is set to type einstein_gpt__caseEmailDraft. Salesforce treats this type as a signal: "this prompt template is intended for the Case email compose window." When a template of this type is Published, Salesforce automatically adds it to the picker that appears when a CSR clicks Draft with AI — no custom code, no LWC, no page layout change needed to trigger it.

What this means for the demo vs production: The demo uses the native Draft with AI button. Rohit's custom LWC adds tone controls (shorter / standard / longer) and a "stamp to compose" action that sit on top of the same AI output. The core logic — template selection, personalisation, guardrails — is identical whether triggered from the native button or the LWC. The LWC is a UX layer, not a different architecture.
