How It Works — Architecture Deep-Dive

Use this section to explain the technical architecture to Rohit and Shankar. It covers what you built, where the intelligence lives, and why it is designed the way it is.

What we are using — technology stack

Everything running today uses standard Salesforce licenses only — no Data Cloud, no external APIs, no third-party AI services.

Custom Metadata Type (Template_Scenario__mdt) — standard Salesforce feature, no extra license. Stores the template library with "When to use" descriptions. Queryable from Flow. Editable by admins with no code.

Prompt Flow (Add_Historical_Case_Emails_to_Prompt2) — standard Salesforce Flow, Process Type: PromptFlow. Assembles the full prompt at runtime: reads the current email thread, queries the template library, reads historical closed case emails.

Prompt Template (Custom_CSR_Response) — Einstein Generative AI, included with Agentforce. Receives the assembled prompt and returns the draft to the CSR.

LLM (sfdc_ai__DefaultGPT5Mini) — Einstein AI model, included with Agentforce. Does the template selection and email drafting.

Data Cloud — NOT in use today. It is on the roadmap as a Phase 3 option if Type/Reason tagging alone is not precise enough to retrieve the right templates from a large library. The customer confirmed they are open to it if needed, but it is not required to make the current architecture work.

Why two prompt templates instead of one

The original design used a single prompt template for both first-contact and follow-up replies. During testing this created an irresolvable conflict: the first-contact template body contains the full document checklist as mandatory language (Form AM-CMD-001, medical license, W-9). Instruction 4 in the prompt said "do not remove mandatory language." A follow-up reply instruction said "do not repeat the checklist." These two rules fought each other on every reply — Instruction 4 won because it was unconditional, so the checklist always appeared even in replies where the customer already had it. No amount of prompt instruction tuning resolved it because the conflict was structural, not phrasing-related.

The fix is architectural: two purpose-built prompts with no conflicting responsibilities. The First Contact prompt is allowed to include the full checklist and is designed to do so. The Reply prompt never sees a template with a checklist in it — its job is to read the thread and answer questions. Each prompt does one thing with no internal contradictions.
Prompt 1 — CSR First Contact Email
When to use: Opening a new case with no prior email thread. The CSR has not yet contacted the customer.

What it does: Reads Case Type + Reason, selects the best matching template from Template_Scenario__mdt, outputs the full email including the complete document checklist and all submission requirements exactly as written in the template.

File: Custom_CSR_Response.genAiPromptTemplate-meta.xml
Label: CSR First Contact Email
Type: einstein_gpt__caseEmailDraft
Prompt 2 — CSR Reply Email
When to use: The case already has an email thread. The customer replied with questions or follow-up. The CSR needs to respond — not restart.

What it does: Reads all EmailMessages on the case (via the same Prompt Flow), identifies the customer's specific questions from the latest message, drafts a focused reply that answers those questions. Never repeats the document checklist. Never re-explains what the customer already knows.

File: Custom_CSR_Reply.genAiPromptTemplate-meta.xml
Label: CSR Reply Email
Type: einstein_gpt__caseEmailDraft
Advantages of two prompts
• No conflicting instructions — each prompt has one job

• The checklist suppression is guaranteed by the prompt body, not by fragile LLM instruction tuning

• First Contact can be made more aggressive about including mandatory language without risk of it bleeding into replies

• Reply can be made more aggressive about brevity and focus without risk of it stripping mandatory language from first contacts

• Each prompt can evolve independently as requirements change

• The CSR's intent is explicit — they chose "Reply" or "First Contact," so there is no ambiguity about what the AI should produce
Trade-off acknowledged
The CSR now picks between two buttons instead of one. This is a small UX cost. The alternative — a single prompt that detects context and switches behaviour — sounds simpler but is not: LLM instruction conflicts at the prompt level are hard to reason about, hard to test, and degrade unpredictably as the template library grows. Two explicit choices scale better than one clever one.

In the Service Console these appear as two named options under "Draft with AI." For production, the labels can be renamed to anything that makes sense to the CSR team — "New Email" and "Reply to Customer" for example.

The three moving parts

1. Two GenAI Prompt Templates
The instruction sets for the LLM. First Contact selects a template and outputs the full email including mandatory checklist. Reply reads the thread and answers questions without repeating what was already sent. Both pull from the same Prompt Flow data source.

Both use type einstein_gpt__caseEmailDraft — this activates the native "Draft with AI" picker automatically. No LWC needed to surface them.
2. Prompt Flow
A standard Salesforce Flow that runs before either prompt generates. It does three things: (1) reads existing EmailMessages on the current case and labels each [Customer] or [CSR], (2) queries Template_Scenario__mdt filtered by Case Type + Reason to fetch the top 5 matching templates, (3) queries closed historical cases with the same Type + Reason and reads their outbound emails for tone grounding. One shared flow feeds both prompts.

File: Add_Historical_Case_Emails_to_Prompt2.flow-meta.xml

Inside the Prompt Templates — what each section does

Both prompt templates share the same four-section structure. The sections are assembled in sequence by the Prompt Flow and sent to the LLM as a single prompt. The key difference between the two templates is in Section 4 (Instructions) — the First Contact prompt instructs the LLM to select a template and include the full checklist; the Reply prompt instructs it to read the thread and answer questions only.

Section 1 — CURRENT CASE   (the signal)
Injects live Case data using Salesforce merge fields at runtime. The LLM reads Type, Reason, Subject, and Description to understand what kind of case it is dealing with. The merge fields resolve to real values before the LLM sees the prompt.
### CURRENT CASE Case Number: {!$Input:Case.CaseNumber} Type: {!$Input:Case.Type} Reason: {!$Input:Case.Reason} Description: {!$Input:Case.Description} Customer: {!$Input:Case.Contact.FirstName} {!$Input:Case.Contact.LastName} Account: {!$Input:Case.Account.Name} CSR Name: {!$Input:Sender.FirstName} {!$Input:Sender.LastName}
What to say to the customer: "The purple tokens are Salesforce merge fields. They resolve to real values at runtime — the LLM never sees {!$Input:Case.Type}, it sees 'Account Support'. This is standard Salesforce merge field syntax, nothing custom."
Section 2 — CANDIDATE EMAIL TEMPLATES   (the selection logic)
The Prompt Flow queries Template_Scenario__mdt (a Custom Metadata Type) filtered by the case's Type and Reason, fetches the top 5 matching records, and injects them here at runtime. Each record has a When to use: description that tells the LLM when to pick it. The LLM reads the case context, compares it against the candidate descriptions, selects the best match, and drafts using its body. Adding new templates requires no code change — just add a new Custom Metadata record with the right Type, Reason, and When to use text.
### CANDIDATE EMAIL TEMPLATES Choose the single most appropriate template based on Case Type, Reason, and Description. After selecting, use it as your structural foundation — fill in all placeholders with real case values. Do NOT remove, reorder, or paraphrase any mandatory language, form names, or legal statements. TEMPLATE A: Credentialing - Medical Director Change Request Use when: Case involves a request to change or update the Medical Director on a credentialed account. --- [full email body — Form AM-CMD-001, 5–7 business days, placeholders] TEMPLATE B: Credentialing - New Practice Enrollment Use when: Case involves a new practice or facility requesting to enroll as an Allergan Moxie provider. --- [full email body — Forms AM-PE-002 + AM-PC-005, 10–14 business days] TEMPLATE C: Product Support - Not Eligible for Products Use when: Case involves a provider being informed they do not meet eligibility requirements. --- [full email body — Form AM-EL-010, 30-day dispute window] TEMPLATE D: Patient Support - Treatment Planning Use when: Provider is contacting before a patient treatment session — confirming documentation, consent, and product availability. --- [full email body — Form AM-PC-005, AM-TR-001, AM-AE-003, 24hr AE window, 48hr product request notice] TEMPLATE E: Patient Support - Adverse Event Report Use when: Provider reports a patient adverse event or unexpected reaction following Allergan Moxie product administration. Compliance-sensitive. --- [full email body — Form AM-AE-003 (72hr deadline), Section 4.2 compliance warning, 1 business day clinical follow-up]
This is the key design decision. Rather than asking the LLM to write an email from scratch — which risks hallucinating form numbers or SLAs — we give it the pre-approved templates as structure. The LLM's job is to pick the right one and fill the placeholders. It cannot rewrite the mandatory language. Think of it as: the template is the rails, the LLM is the engine that personalises the journey.
Section 3 — HISTORICAL CONTEXT   (the tone calibration)
A single merge field that expands at runtime to the outbound email bodies of up to three previously closed cases with the same Type and Reason. The Prompt Flow queries these records and produces this text before the LLM generates. The LLM uses the examples to calibrate tone — it learns how your experienced reps write, not from generic training data.
### HISTORICAL CONTEXT The following are real outbound responses from similar closed cases. Use these to calibrate tone and solution steps — but always use the selected template above as your structure: {!$Flow:Add_Historical_Case_Emails_to_Prompt2.Prompt}
What to say to the customer: "This one token expands to the actual email text your experienced reps wrote on similar closed cases. The AI learns your team's tone from real examples. In the production version, as your team closes more cases, the grounding pool improves automatically."
Section 4 — INSTRUCTIONS   (the guardrails — different per prompt)
This is where the two prompts diverge. The First Contact prompt instructs the LLM to select a template and preserve all mandatory language. The Reply prompt instructs it to suppress the checklist and focus only on the customer's questions.

First Contact prompt instructions

### INSTRUCTIONS (CSR First Contact Email) 1. Select the best matching template. State: "Selected template: [Name]" 2. Output the complete email body — fill every [placeholder] with real values. Include the full document checklist and all submission requirements exactly as written in the template. 3. Do NOT invent form names, case numbers, or contact details. 4. Do NOT remove any form names, legal statements, or processing time commitments from the template. 5. Adjust tone to be warm and professional. 6. End with the CSR Name from the CURRENT CASE section above — do not use any name from the email thread.

Reply prompt instructions

### INSTRUCTIONS (CSR Reply Email) 1. Read the CURRENT EMAIL THREAD. Identify the customer's specific questions from their most recent message. 2. Draft a reply that directly answers each question. Do not pad or deflect — answer what was asked. 3. Do NOT repeat the document checklist or submission requirements already sent. No numbered list, no "please submit X, Y and Z", no "the required items remain". Skip the checklist entirely. Exception: if the customer asks about one specific named document, address only that document. 4. Do NOT invent form names, case numbers, policies, or contact details. 5. Acknowledge the prior exchange briefly — do not open with a generic "thank you for contacting us." 6. Keep the response focused and concise. No filler sections. 7. End with the CSR Name from the CURRENT CASE section above — do not use any name from the email thread.
Why the Reply prompt explicitly bans specific phrases: "no numbered list", "no 'the required items remain'" — these are the exact patterns the LLM used when we had a single prompt. The Reply instructions were written by looking at actual failure outputs and banning them by name. This is normal for production prompt engineering.

Why Template_Scenario__mdt — the reasoning behind the architecture

This is the question Rohit or the customer team will almost certainly ask. Here is the full reasoning so you can answer it confidently.

Why not hardcode the templates directly in the Prompt Template?
That was the original POC approach. It worked for 3 templates in a demo but it does not scale. The prompt has a size limit. With dozens of templates embedded as text, you hit that limit quickly and the LLM also struggles to reason across too many options at once. Every time a template needed editing, it required a metadata deployment — something the content team cannot do themselves. Hardcoding also mixes instructions and data in the same file, which is poor practice for anything that needs to be maintained over time.

Why not use Salesforce's standard EmailTemplate object?
This was the obvious first choice. The problem: Salesforce does not allow custom fields on the EmailTemplate standard object. We needed one key field — When_To_Use__c — a plain-English description of when a CSR would reach for this template. Without that field, the LLM has no signal to distinguish between templates beyond their body text. That makes accurate selection unreliable, especially when two templates look superficially similar. We hit the custom field restriction during deployment and had to find a better path.

Why Custom Metadata Type (Template_Scenario__mdt)?
Custom Metadata Types are a Salesforce-native pattern designed exactly for configuration data that needs to be: (1) deployable as code, (2) queryable from Flow and Apex, and (3) editable by admins without a developer. We created Template_Scenario__mdt with the fields we needed — including When_To_Use__c and Template_Body__c. The Prompt Flow now queries it at runtime, filters by Case_Type__c and Case_Reason__c, and passes a shortlist of up to 5 matching templates to the LLM. The LLM reads each template's "When to use" description alongside the case context, picks the best match, and drafts using that template's body.

What this means for the customer's ~1,600 templates:
To scale to the full library, the customer creates one Template_Scenario__mdt record per template. Each record needs: the template body, a one-sentence "When to use" description, and the Case Type and Reason it applies to. No code, no deployments — this is a data entry task their content team can own via Setup → Custom Metadata Types → Template Scenario → Manage Records, or bulk-loaded via Data Loader.

What comes after CMT — Phase 3 vector search (not in use today):
CMT with Type/Reason filtering works well when templates map cleanly to case categories. If it turns out that experienced CSRs pick templates based on subtle judgment that cannot be expressed as a simple Type/Reason tag — for example, two very different situations that both fall under "Account Support / Credentialing" — the next step would be semantic vector search via Data Cloud. Templates would be vectorised once. The case thread becomes the search query. Vector similarity surfaces the closest matches regardless of tagging. The LLM still does the final selection from the shortlist. This is a future decision — the customer does not need Data Cloud to start loading their template library into CMT and testing today.

How the type activates the native "Draft with AI" button

The Prompt Template is set to type einstein_gpt__caseEmailDraft. Salesforce treats this type as a signal: "this prompt template is intended for the Case email compose window." When a template of this type is Published, Salesforce automatically adds it to the picker that appears when a CSR clicks Draft with AI — no custom code, no LWC, no page layout change needed to trigger it.

What this means for the demo vs production: The demo uses the native Draft with AI button, which now shows two options: CSR First Contact Email and CSR Reply Email. Rohit's custom LWC adds tone controls (shorter / standard / longer) and a "stamp to compose" action on top of the same AI output. The core logic — template selection, personalisation, guardrails, two-prompt separation — is identical whether triggered from the native button or the LWC. The LWC is a UX layer, not a different architecture. In the LWC, the two prompts can be surfaced as a single toggle ("New email / Reply") rather than two separate picker options if preferred.

What to say about the gaps — use this word for word
"Everything you see today is live in a Salesforce org. The core intelligence — pick the right template, preserve mandatory language, personalise with case context — is working. The template library is no longer hardcoded. It is a Custom Metadata object called Template Scenario. Right now it has three records — your three demo templates. To get to your full library, your team creates one record per template with the template body and a one-sentence description of when to use it. No code, no deployments — it is a data entry task your content team can own. Tone controls and the stamp action are already in your LWC; we connect the prompt output to those controls. Category and Sub-Category filters are a 30-minute change the moment you give us the API field names. None of these are rebuilds."
One structural gap to be fully transparent about: EmailMessage in Salesforce does not natively record which EmailTemplate was used to compose an outbound email. If you want to score templates by frequency of use by experienced reps in Phase 3, your team will need to add a custom lookup field to EmailMessage and populate it at send time. This does not affect anything in the current demo — it is a future data foundation decision, and it is better to surface it now than to discover it late in the project.
