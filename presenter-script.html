Architecture - How It Works
Keep it to 2 minutes - no deep dive here
5 min
Open this file
→Open demo-walkthrough.html and click the Flow Diagram tab
Say this - point at the diagram as you go
So when the CSR clicks Draft with AI, this is what happens in the background.
Step 1 - A Flow runs. It looks at the case and reads two fields: Case Type and Case Reason. Those two fields are your routing gate.
Step 2 - It goes to a lookup table we built - think of it like a phone book. You give it a Case Type and Reason, it gives you back the name of the correct email template. That lookup table is called a Custom Metadata Type - it's admin-managed, no code needed to update it.
Step 3 - It fetches the body of that email template. The full policy text goes into the AI prompt.
Step 4 - If there is an email thread on the case, it reads that too and tells Einstein to take it into account when drafting the reply.
Step 5 - Einstein writes the draft and it appears in the email composer. Done.
If they ask a technical question here
What if the Case Type or Case Reason is blank - or doesn't match anything in the lookup table?
The system still produces a draft - it never crashes or shows an error to the CSR. But instead of using your policy template, it falls back to a generic message and tells Einstein: "No matching template was found - draft a professional response based on the case details." So the draft will look polished but it won't have your form references, SLAs, or compliance language. It's essentially Einstein guessing from the case subject. The CSR needs to catch that in their review - which is exactly why the human stays in the loop. And it's a clear signal to go and add that case type to the routing table.
How do you add a new template? - Two steps: create the email template body, add one row to the lookup table. Admin task, no code, no deployment.
What AI model is it using? - GPT-4o Mini via Salesforce's Einstein AI - fully within the Salesforce trust boundary, no data leaves your org.

Part 2 - What is open and what comes next 15 min

The Gaps
Be transparent - don't avoid this section
5 min
Say this
There are two things the current solution does not do - and I want to be upfront about them.
Gap 1 - Historical learning. Your original ask was for the AI to look at past closed cases, see which templates experienced reps used, and recommend the winning template. We didn't build that - and here's why.
The voting model has a flaw: different reps have been using different templates for the same case type for years. If the AI learns from that history, it learns inconsistency. The approach we took instead is deterministic - an admin defines the correct template for each case type, and the AI enforces it every time. It's more reliable and you control it directly.
Gap 2 - Audit trail. Right now the system does not record which template was used on which email after it's sent. So you can't go back and report on template usage across your team. That's a known gap and it has a clean fix - which I'll cover in the options.
Key message: These are gaps by choice on the historical learning side, and a missing feature on the audit side. Neither blocks the core value you just saw in the demo.

Three Options
Walk through each option - end with a recommendation

Option 1 - say this
Option 1 is what you just saw. It's live today. The components we built are: a Prompt Flow that handles routing and context assembly, a Custom Metadata Type that is your routing table, two Prompt Templates for first contact and reply, and the 10 email templates. Everything is admin-manageable going forward - no code needed to add new scenarios.
Option 2 - say this
Option 2 adds Data Cloud for historical learning. This is how you get closer to the original ask - the AI seeing patterns from past cases. Data Cloud ingests your CRM data, builds Calculated Insights from closed case history, and makes those insights available inside the Prompt Builder. So the AI can factor in what your best reps have done before.
Important caveat - your current Data Cloud usage is knowledge articles only. Wiring in CRM objects and building the insights pipeline is a meaningful engagement. This is Option 1 first, then Option 2 once Option 1 is live and validated in production.
Option 3 - say this
Option 3 fixes the audit trail gap by extending your existing custom LWC component. When the CSR sends an email, the LWC stamps a field on the EmailMessage record recording which template was used. You can then report on it - which templates are being used, by which reps, for which cases.
It can also auto-select First Contact or Reply based on whether a thread exists, so the CSR doesn't need to make that choice. Your development team builds this - we can provide the spec.
Recommendation - say this to close
My recommendation is Option 1 now, Option 3 next. Option 1 is already done. Option 3 closes the audit gap and is a clean scoped piece of work for your dev team. Option 2 is the longer-term path if historical learning becomes a priority after the core solution is validated in production.

Questions & Next Steps
Common questions you're likely to get - with short answers
5 min
Questions you will likely get
What happens if the case type doesn't match any template?
The AI still produces a draft - but it's a generic one based only on the case description. No policy language, no form references. It looks fine on the surface. That's why the human review step matters. And it's a signal to build that CMT record next.
What if the CSR edits the draft heavily - does the AI learn from that?
No - not in the current setup. The AI produces a fresh draft each time from the same inputs. If you want the AI to learn from edits over time, that is an Option 2 conversation.
How do we get from 10 templates today to the full library?
Two steps per scenario: write the email template body, add one row to the routing table. Your content team or admin can do this. No development needed. Start with your top 15–20 highest-volume case types and you'll cover the majority of your cases.
What does production deployment look like?
The components are all standard Salesforce metadata - they deploy via a package. The main work before go-live is populating the routing table with your active case types and getting your email template content reviewed and signed off.
