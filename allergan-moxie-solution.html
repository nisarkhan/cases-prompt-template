Solution Overview
A focused summary of the problem, what has been solved today, what the gaps are, and three options to close them.
Discovery
What the team is dealing with today
Captured directly from the customer discovery session with the Provider Services team.
Core Problem
CSRs spend 20 minutes drafting every provider email - and there is no reliable way to pick the right template
The org has approximately 1,600 email templates built up over many years. When a provider case comes in, a CSR must know from experience which template applies. New joiners have no idea - they ask a colleague or guess. Even experienced reps use different templates for the same case type, leading to inconsistent responses and missed policy requirements.

The Provider Services team came in with one core problem: CSRs — especially new joiners — have no reliable way to know which email template to use out of approximately 1,600 email templates in the org. Different reps use different templates for the same case type, leading to inconsistent responses and missed policy requirements.
Their original ask was for Agentforce to look at historically successful closed cases, learn which templates experienced reps used, and recommend the "winning" template for each new case — essentially a voting model based on past rep behaviour.
They also wanted the system to read the full email thread on a case before drafting a reply, so CSRs are not repeating information already sent. And they wanted a human in the loop — the CSR reviews and approves every draft before it goes out.
🔍

📋

Form references, SLA timelines, compliance statements - if the CSR picks the wrong template or forgets a field, the provider gets incomplete information and the case requires a follow-up.
⏱️
20 minutes per email - manually
Find the right template, copy the body, personalise with provider details, check the email thread to avoid repetition, verify nothing was missed. All done by hand, every single time.

How it works in one paragraph
1
CSR clicks "Draft with AI" on the case
Selects First Contact (new case) or Reply (ongoing thread). That is the only decision the CSR makes.
2
System reads Case Type + Case Reason and finds the right template
A routing index (Custom Metadata) maps the case to the correct email template. Out of 1,600 templates, the right one is fetched in under a second.
3
Einstein AI personalizes the draft
The template body provides the policy-accurate structure. The case description, provider name, and email thread provide the personalisation. Einstein combines both into a complete draft.
4
CSR reviews and sends
The draft appears in the Salesforce email composer. CSR reads it, edits if needed, and sends.
Proof of concept scope This has been built and tested against 10 scenarios covering credentialing and patient support cases. The architecture supports as many scenarios as needed - extending it to the full template library is an admin and content exercise, not a development task.
Gaps
What is not in the current proof of concept
Two gaps remain from the original ask. Both are addressable - the right path depends on how the customer wants to proceed.
1
Historical case learning - the "voting model"
Not in POC
The team asked for the AI to look at historically successful closed cases, see which templates experienced reps used, and vote on the best template. The current solution uses a deterministic routing rule instead - the admin defines which template applies to which case type, and the AI enforces it every time.
Why the current approach is actually stronger The voting model has a fundamental flaw the customer discussion itself revealed - different reps used different templates for the same case. A vote would pick whoever handled the most cases, not whoever was most accurate. The routing rule model puts the right human (your compliance team) in control of what is correct, then enforces it consistently. If historical learning is still wanted, it is addressed in Option 2 and Option 3 below.
2
No audit trail - which template was used to generate the email
Not in POC
Once an email is sent, there is no record stored on the case of which template the AI used to draft it. The team specifically asked whether this could be tracked. The standard Salesforce EmailMessage object does not store this today.
Fix path A custom field on EmailMessage stamped at send time - either through a custom LWC component or a Flow trigger. This is a targeted, low-risk development task. It does not require changes to the AI routing layer.
3
Custom LWC component - Draft with AI not embedded in the existing UI
Not in POC
The team currently uses a custom LWC component with its own navigation to reach the email composer. The proof of concept uses the standard Agentforce "Draft with AI" button. The AI drafting capability is not yet embedded in the existing CSR workflow - meaning additional clicks are required today.
Fix path Embed the Draft with AI trigger inside the existing custom LWC component. The AI routing layer (CMT routing, Prompt Flow, EmailTemplates) stays exactly the same. Only the surface the CSR interacts with changes. This can be combined with Gap 2 into a single scoped LWC development engagement.
All three gaps are addressable - see the Three Options tab for recommended paths forward Gap 1 (historical learning) can be addressed through Data Cloud or the existing custom LWC. Gaps 2 and 3 are both custom LWC development tasks that can be delivered together in a single engagement.

2
Future Enhancement - Historical Learning
Option 1 + Data Cloud
Add historical email retrieval and template usage analysis on top of the existing routing layer using Salesforce Data Cloud
Future phase
What it adds
Data Cloud unifies the historical EmailMessage records stored in Salesforce with the case data. It can surface patterns - which templates were used on successfully closed cases with the same case type, which produced the fewest follow-up emails, which had the shortest time to close. This information can be passed into the AI prompt as additional context to influence template selection or to surface a recommendation to the CSR alongside the AI draft.
Data Cloud features used
1
Salesforce CRM Connector
Native connector that ingests Case and EmailMessage records from the Salesforce org into Data Cloud. This is the data pipeline - pulls all historical closed cases and the emails sent on each one.
2
Data Streams → Data Lake Objects (DLOs)
Once ingested, Case and EmailMessage data lands in Data Lake Objects - the raw storage layer inside Data Cloud. Each CRM object becomes a DLO that can be queried and modelled.
3
Data Model Objects (DMOs)
Maps the raw DLOs to harmonized Data Model Objects - normalising the data so Case and EmailMessage records can be joined and queried consistently. Case maps to an Engagement or Case DMO.
4
Calculated Insights - the "voting model"
A saved SQL-style query that runs over the Data Cloud data and produces an aggregated metric. The Calculated Insight asks: "for each Case Type + Case Reason combination, which Email Template appears most frequently on successfully closed cases?" - that is the vote count. This is the core feature for the historical learning capability the customer asked for.
5
Data Cloud Data Provider in Prompt Builder
Prompt Builder has a native Data Cloud data provider. The Calculated Insight result is surfaced directly into the Prompt Template - so Einstein sees both the CMT routing match and the historical vote context (e.g. "this template was used on 47 successfully closed cases of this type") when generating the draft.
Important caveat: The customer's current Data Cloud usage is limited to knowledge articles. Ingesting CRM objects, building Calculated Insights, and wiring into Prompt Builder is a meaningful configuration effort - a scoped Data Cloud engagement, not a quick admin task. Recommended after Option 1 is live and validated in production.

The customer already has a custom LWC component that CSRs use to navigate cases and compose emails. What the customer needs to do
1
Share the existing LWC component codebase
The customer already has a custom LWC used by CSRs to navigate cases and compose emails. The developer needs read access to that component's code - specifically the method that opens the email composer - so the Draft with AI trigger can be wired in at the right point in the existing user flow.
2
Add a custom field to EmailMessage
Create a custom text field on the EmailMessage object (e.g. AI_Template_Used__c) to store the name of the template that was used to generate the draft. This is the audit trail field - it gets stamped at send time by the LWC.
3
Extend the LWC to call the Prompt Template API
Add a "Draft with AI" button or trigger inside the existing component. When clicked, the LWC calls the Agentforce einstein_gpt__caseEmailDraft action - the same action the standard button uses - and populates the email composer with the returned draft. No changes to the Prompt Template or Prompt Flow are needed.
4
Stamp the template name on EmailMessage at send
When the CSR clicks Send, the LWC writes the template name returned by the Prompt Flow into the AI_Template_Used__c field on the EmailMessage record before saving. This can also be done via a before-insert Flow trigger on EmailMessage if the LWC approach is not preferred.
5
Deploy and test in sandbox first
All LWC changes should be deployed to a sandbox and tested against the existing test cases (Part A - First Contact and Part B - Reply) before going to production. The AI routing layer (Prompt Template, Prompt Flow, CMT, EmailTemplates) is unchanged - only the surface the CSR interacts with is modified.
What stays the same: The Prompt Template, Prompt Flow, CMT routing records, and EmailTemplates are not touched. The developer only modifies the existing LWC - the AI layer is already built and working.

Areas We Are Exploring
What happens when Case Type + Reason don't match
The system always produces a draft — it never blocks the CSR. But the quality of that draft depends on whether a routing match was found. These are the four scenarios to be aware of.
1
No CMT record exists for this Case Type + Reason
Silent failure — most critical
The Prompt Flow finds zero matching records in the CMT routing index. It hits the fallback branch and injects this message into the prompt instead of a template body: "No matching email templates were found. Draft a professional response based on the case details above."
Einstein still produces a draft that looks polished and professional — but it has no form references, no SLAs, no mandatory compliance language. The CSR receives a draft that looks fine on the surface and may send it without realising critical policy requirements are missing.
Why it's the most critical
The failure is invisible. There is no error message, no warning in the draft. A CSR has no way of knowing the template was missing unless they already know what the correct output should look like.
How to address it
Start with the top 10–15 highest-volume case types. Build CMT records for those first. Use cases that produce generic drafts as a signal of what to build next — not a system failure, a prioritisation queue. The key question to ask the customer is: "Of the 1,600 templates, how many are actually still in active use?" — in most orgs, a large percentage are legacy or duplicates. That audit will likely shrink the real number significantly.
2
Multiple CMT records match the same Case Type + Reason
Future consideration
If the same Case Type + Reason combination maps to more than one template — for example, different responses depending on provider specialty or plan type — the CMT lookup returns multiple rows and the system needs to decide which one to use.
How it is handled today
The When_To_Use__c field is already built for this. The Prompt Flow passes all candidate templates and their When_To_Use__c descriptions to Einstein, which picks the most appropriate one based on the case context.
POC status
All 8 current routing records are unique Type + Reason combinations, so this scenario does not come up in the POC. Worth flagging to the customer as a future consideration when they expand the template library.
3
Very long email threads approaching token limits
Production consideration
Einstein AI models available through Salesforce support context windows in the range of approximately 16K–32K tokens depending on the model selected in the Prompt Template (GPT-4o Mini vs GPT-4o). A single email is roughly 200–500 tokens, so a thread of 30 or more emails could start pushing against those limits.
POC status
Not an issue in the POC — test threads are short. The Prompt Flow already caps the current thread at 5 emails and historical cases at 3. This is a production consideration for cases with very long back-and-forth history.
Recommended approach for production
Truncate to the last 10–15 emails in the Prompt Flow, or summarise older messages before passing them to Einstein. This is a Flow configuration change — no changes to the Prompt Template needed.
4
CSR selects First Contact template on a reply case (or vice versa)
Handled by design
Keeping First Contact and Reply as two separate Prompt Templates was a deliberate design choice — it avoids instruction confusion in the LLM. Each template has a distinct set of instructions appropriate for its context. The CSR selects which one to use from the "Draft with AI" menu, so the responsibility stays with them.
Why this is not a system problem
If a CSR selects First Contact on a case that already has an email thread, Einstein still reads the thread (the Prompt Flow always injects it) and instruction 7 in the First Contact template tells it to treat the presence of a thread as a reply signal. The output will still be reasonable — not ideal, but not broken.
Best handled via Option 3 (custom LWC)
If the customer wants to eliminate the choice entirely, the custom LWC can auto-select the correct template based on whether an email thread exists on the case — First Contact if no thread, Reply if a thread is present. No CSR decision needed.
Summary — how to think about these during rollout
Scenario 1 — prioritise prevention
Generic drafts will appear for case types without a CMT record. Expected during rollout — treat each one as a signal of a template to build next. Ask the customer to audit how many of the 1,600 templates are actually still in active use. The real number is almost always much smaller.
Scenarios 2 & 3 — future-proof considerations
Multiple matches are already handled by When_To_Use__c — not a concern for the POC. Token limits are not an issue with short threads but worth addressing in the Prompt Flow before production go-live.
Scenario 4 — handled well by design
Two separate templates avoids LLM instruction confusion. The custom LWC (Option 3) can auto-select the right template based on whether a thread exists — removing the CSR decision entirely if the customer wants that.
None of these block the POC
All four scenarios are either already handled, not applicable to the current 8-template scope, or production considerations. The POC can proceed and these are framed as transparent discussion points with the customer.
