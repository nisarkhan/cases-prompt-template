Customer Summary

What changed and what you are testing

The template body used to live inside the Custom Metadata Type record (Template_Body__c). It now lives in a native Salesforce Email Template. The CMT record holds only a pointer - the Email_Template_API_Name__c field - and the Prompt Flow fetches the body at runtime by querying EmailTemplate WHERE DeveloperName = {pointer}.

OLD: CMT record → Template_Body__c (body stored directly on CMT) NEW: CMT record → Email_Template_API_Name__c → EmailTemplate.Body (fetched at runtime)

The end result for the CSR is identical - same draft, same quality. What changes is where the content team edits template language: Setup → Email Templates → Allergan Demo Templates folder, not Custom Metadata records.

Run through these four checks first. Each one is a 30-second confirmation that the deployment landed correctly. If any check fails, the fix is in the steps below.

Check 1 - CMT field

  1. Go to Setup → Custom Metadata Types → Template Scenario → Fields
  2. Confirm Email Template API Name field exists (Text, 255)
  3. Confirm Template Body field still shows but has no values - open any record and verify the Template Body field is blank

Fail - Email Template API Name missing: Run sf project deploy start --source-dir force-app/main/default/objects/Template_Scenario__mdt -o allergan-moxie and re-check.

Check 2 - CMT records have the pointer set

  1. Go to Setup → Custom Metadata Types → Template Scenario → Manage Records
  2. Open any record - for example AM Medical Director Change
  3. Confirm Email Template API Name shows Credentialing_Medical_Director_Change
  4. Confirm Template Body is blank
Pass: Email Template API Name populated. Template Body blank.

Check 3 - EmailTemplate records exist in the org

  1. Go to Setup → Email Templates
  2. Open the Allergan Demo Templates folder
  3. Confirm all 10 template DeveloperNames are listed - the 6 credentialing templates and 4 patient journey templates
  4. Click into one - for example Patient Adverse Event - and confirm the body text is visible (not blank)
Pass: All 10 templates present in the folder with body text.
Fail - templates missing: Run sf project deploy start --source-dir force-app/main/default/email -o allergan-moxie

Check 4 - Flow is Active and has the new lookup node

  1. Go to Setup → Flows → Add Historical Case Emails to Prompt2
  2. Confirm status is Active
  3. Click into the flow - inside the template loop, look for a node called Get Email Template Body
  4. Confirm Append Template Entry assignment uses {!Get_Email_Template_Body.Body} - not {!CurrentTemplate.Template_Body__c}
Pass: Flow Active. Get Email Template Body node present. Append Template Entry uses the new reference.
Fail - old flow still active: Run sf project deploy start --source-dir force-app/main/default/flows -o allergan-moxie

Solution Scope - What We Built, What the Gaps Are, and How to Think About It

This is a proof-of-concept and a working demonstration of the core AI routing capability - not a finished end-to-end production system. The goal is to show the customer what is possible with Agentforce and give them a clear path forward to build the full solution on their own platform.

How to position this to the customer: "We are not handing you a finished product. We are proving that the core capability works - AI reads a case, finds the right policy template automatically, and produces a personalised, compliance-accurate draft. The plumbing is real and tested. What you build on top of it is yours to extend."

What We Built - Working and Tested

AI template routing - deterministic and reliable
Case Type + Case Reason → CMT routing index → EmailTemplate body fetched at runtime. Tested across 10 templates and 8 routing rules covering credentialing and patient support scenarios. Zero hardcoded content in the Flow.
Two entry points - First Contact and Reply
Custom GenAI Prompt Templates for both scenarios. First Contact generates an opening email with the full policy checklist. Reply reads the full email thread and answers the provider's specific questions without repeating what was already sent.
Two-layer intelligence - policy structure + personalisation
EmailTemplate body = mandatory policy language (forms, SLAs, compliance statements) that the AI cannot change. Case description + thread = personalisation layer. Both layers proven in live testing against real cases (00001156, 00001157).
Content team ownership - no deployment for template edits
EmailTemplate bodies live in Setup → Email Templates. Content and compliance teams can edit policy language instantly without admin access or deployment. CMT routing records are managed by admin with no code changes.
Extensible by design - new scenarios in two steps
Adding a new scenario requires only: create an EmailTemplate body + create a CMT routing record pointing to it. No Flow changes, no developer needed. Proven architecture pattern.

Gaps - What Is Not in This Proof of Concept

Gap 1 - Historical case mining and template voting
What the customer asked for: The system should look at historically successful closed cases, see which templates experienced reps used, and vote on the "winning template" - essentially learning from past rep behaviour.

What we built instead: Deterministic routing - Case Type + Reason → CMT → right template, every time.

Why our approach is actually better: The customer's own transcript reveals the problem with the voting model - different reps used different templates for the same case. Rohit used one, others used another. A vote would pick whoever handled the most cases, not whoever was most accurate. Our CMT routing puts the right human (your compliance team) in control of which template is correct, then enforces it consistently. That is more reliable and auditable than learned behaviour.

If they still want historical mining: This would require Data Cloud or a custom analytics layer to read EmailMessage history, identify which template was used per case outcome, and surface a recommendation. That is a separate, larger engagement - not part of this proof of concept.
