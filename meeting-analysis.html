Critical clarification from the diagram: The two paths are NOT about "Web-to-Case vs Email-to-Case" at the technical level. They are about whether any outbound email has already been sent on this case. A new Web-to-Case will follow the LEFT path. An Email-to-Case that already has a reply thread follows the RIGHT path. Your flow needs to detect this at runtime.

🖥️ The Custom LWC Component — What They Built & What It Does

From Rohit's demo in the meeting, the team already has a custom LWC (Lightning Web Component) embedded on the Case record. This is NOT the native Service Grounding "Draft with AI" button — it's a custom component they built themselves. Here's what it does:

What the LWC already does

  1. CSR clicks a custom button on the Case page (Rohit showed this — a "Generate Draft" style button in the email area).
  2. Component reads Case attributes (status, category, subcategory, comments, existing emails).
  3. Calls a Prompt Template behind the scenes that generates a response draft.
  4. Displays the draft to the CSR.
  5. CSR reviews it. If satisfied, clicks another button to stamp the draft into the email compose window.
Business pushed back on this. Rohit said: "When we did that show and tell to the business, they were like, no, we want more, more to this. More flavors to it." — The draft was generated freely without reference to their official email templates, so it didn't match the expected structure.

🎯 What the Customer Is Actually Asking For (Complete Picture)

Combining the diagram + meeting transcript, the full requirement is:

Path A — New Case (no email yet)

  1. Read Case: Type, Reason, Category, Sub-Category, Record Type
  2. Query historical closed cases with same attributes
  3. From those cases, find which email templates were used for outbound replies
  4. "Vote" — most-used template by experienced reps wins; factor in resolution speed
  5. Fetch the winning EmailTemplate.Body
  6. LLM fills merge fields (name, case #, forms)
  7. CSR picks tone (shorter / standard / longer)
  8. LWC stamps draft → CSR reviews → sends

Path B — Existing Case (has reply thread)

  1. Read all emails on this case (inbound + outbound) in chronological order
  2. Read Case: Status, Category, Sub-Category
  3. Understand context: is this a follow-up? Are forms pending? Is there a delay?
  4. Ground reply on the current conversation thread — do not repeat what was already said
  5. May still reference historical templates for format, but conversation context takes priority
  6. LLM injects current Case attributes (status update, form names)
  7. CSR picks tone
  8. LWC stamps draft → CSR reviews → sends
The ~1,600 email templates fact: Rohit said they've "been carrying that baggage for a long time." Not all 1,600 are relevant — there are templates per record type (Credentialing, Facial Inbound, etc.) and per scenario. The AI needs to narrow down candidates based on Case attributes BEFORE doing frequency scoring. You don't feed all 1,600 into the LLM.

⚠️ The Core Technical Gap — This Is the Real Blocker

Everything in the customer's design depends on one thing being true: you can look at a past outbound EmailMessage and know which EmailTemplate was used to compose it. That is currently not possible natively in Salesforce.

What Salesforce stores natively

  • EmailMessage.TextBody / HtmlBody — the final sent content
  • EmailMessage.Subject
  • EmailMessage.FromAddress, ToAddress
  • EmailMessage.Incoming (true = inbound, false = outbound)
  • EmailMessage.ParentId → links to the Case
  • EmailMessage.MessageDate
NOT stored: which EmailTemplate was used. When a rep selects a template in the compose window and hits send, Salesforce does not stamp EmailTemplateId on the resulting EmailMessage record.

Two ways to bridge this gap

Option 1 (Recommended — Forward-looking):
Add a custom field EmailTemplate__c (Lookup → EmailTemplate) on EmailMessage. Populate it via a Flow triggered when the LWC stamps the draft (you already control that button). From this point forward, every AI-assisted email is tagged. Historical data won't be available but you build the dataset over time.
Option 2 (Inference — Fragile):
For historical emails already sent, attempt to match EmailMessage.HtmlBody against known EmailTemplate.HtmlValue using fuzzy text comparison. Fragile if reps modified the template before sending. Useful only as a one-time bootstrap exercise.
Interim MVP (no data gap blocker): Skip frequency scoring for now. Instead, use Case Type + Reason + Category + Sub-Category to query EmailTemplate records directly (by name/folder/developer name conventions). Let the LLM pick the best candidate from a filtered shortlist of 3–5 templates. This is feasible immediately without any schema changes.

✅ Verdict — Hybrid Architecture Is the Right Answer

You are right about the architecture: one Prompt Template does orchestrate everything. But it needs to include the Email Template's body as a structural anchor inside the prompt. The diagram Rohit shared is not asking for two separate systems — it is asking for one intelligent flow with two execution paths (new case vs existing case), both powered by the same Prompt Template framework.

They are right about the requirement: The Email Templates contain mandatory language, form references, and brand-specific structure. The LLM must work within the template, not replace it. The tone controls (shorter/longer) only make sense when there's a template to constrain what can change.

The real ask in one sentence: "Use AI to pick the right Email Template, fill its placeholders, let the CSR adjust tone, and stamp the result into the compose window — all without the CSR having to search through 1,600 templates."
