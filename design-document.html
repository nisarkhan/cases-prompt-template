Agentforce Email Draft — Architecture Design Document

Defines the component architecture for AI-drafted CSR emails in the Allergan Moxie Agentforce demo, including the revised data model that eliminates duplication between Custom Metadata Types and native Salesforce Email Templates.

Overview

The Allergan Moxie Agentforce demo surfaces AI-drafted outbound emails directly in a CSR's Service Console. When a case is opened or a reply is needed, an Agentforce Agent Action invokes a Prompt Flow (Add_Historical_Case_Emails_to_Prompt2) that assembles a rich context block — candidate template text, prior thread messages, and historical closed-case examples — and feeds it into one of two GenAI Prompt Templates (CSR First Contact Email or CSR Reply Email). The AI returns a fully drafted message the CSR can review and send without starting from a blank page.

The original implementation stored the full email body in a Custom Metadata Type (CMT) record, duplicating content that already existed in Salesforce's native Email Template object. This meant the content team had to keep two records in sync for every template. The revised architecture treats the CMT purely as a selection index — it maps case attributes to a template API name — while the authoritative body lives exactly once, in the Email Template object. The Prompt Flow resolves the body at runtime via a single query join.

Design Principle
Each template body is written and maintained in exactly one place: the native Salesforce Email Template record. The Custom Metadata Type only says which template to use — it never stores the content itself.

Data Model

The architecture uses two objects in a read-only join at runtime. The join key is Template_Scenario__mdt.Email_Template_API_Name__c matched against EmailTemplate.DeveloperName.

Old Design (Removed)

  • Template_Scenario__mdt stored Template_Body__c (Long Text)
  • Body text duplicated from Email Template
  • Content team updated two records per change
  • Drift risk: CMT and EmailTemplate could diverge silently

New Design (Current)

  • Template_Scenario__mdt is a selection index only
  • Body lives once in EmailTemplate.Body
  • Content team updates one record per change
  • No sync drift possible — single source of truth

Template_Scenario__mdt — Selection Index Fields

Field API Name Type Purpose
MasterLabel Text Human-readable name for the CMT record (e.g., Credentialing Medical Director Change).
Case_Type__c Text Matches Case.Type. Used as the first routing filter (e.g., Account Support).
Case_Reason__c Text Matches Case.Reason. Used as the second routing filter (e.g., Credentialing).
Email_Template_API_Name__c Text (255) Join key. Stores the DeveloperName of the matching Classic Email Template record.
When_To_Use__c Long Text Area Human-readable guidance for when to apply this template. Injected into the AI prompt context as a hint.
Is_Active__c Checkbox Routing toggle. Only records with Is_Active__c = true are returned at runtime.

EmailTemplate — Relevant Fields

Field Name Type Purpose
DeveloperName Text Join target. Must match the value stored in Email_Template_API_Name__c exactly.
Name Text Display label shown in Setup and email template lists.
Body Long Text Area The authoritative email body. Resolved at runtime and appended to the AI prompt context.
Subject Text Suggested subject line. May be included in context depending on prompt configuration.
FolderId Reference All demo templates reside in the Allergan Demo Templates folder for organizational clarity.
Join Query Pattern
The Prompt Flow queries Template_Scenario__mdt filtered by Case Type, Case Reason, and Is_Active__c = true, then for each matching record it runs a second query: SELECT Body FROM EmailTemplate WHERE DeveloperName = :Email_Template_API_Name__c LIMIT 1. This two-step resolution keeps the CMT metadata-only and the body in native tooling.
5

Flow Logic

The Prompt Flow Add_Historical_Case_Emails_to_Prompt2 executes the following steps each time an Agent Action requests an email draft. The Flow receives the current Case record as input and returns a formatted context string that is injected into the active GenAI Prompt Template.

  1. 1

    Collect Email Thread (Path B Only)

    If the case has an existing email thread (Path B), query EmailMessage records related to the case, ordered by MessageDate ASC. Format each message as a labelled block (From, Date, Body) and append to the context. Path A (no prior thread) skips this step entirely.

  2. 2

    Query CMT Selection Index

    Query Template_Scenario__mdt WHERE Case_Type__c = {case.Type} AND Case_Reason__c = {case.Reason} AND Is_Active__c = true. Returns zero or more matching CMT records, each carrying an Email_Template_API_Name__c value and a When_To_Use__c hint.

  3. 3

    Loop: Resolve Email Template Bodies

    For each CMT record returned in Step 2, execute a sub-query: SELECT Body, Subject FROM EmailTemplate WHERE DeveloperName = :Email_Template_API_Name__c LIMIT 1. Append the resolved body, subject, and the CMT's When_To_Use__c hint to the candidate templates section of the context block. If the EmailTemplate record is not found, the loop iteration is skipped gracefully.

  4. 4

    Assemble Candidate Templates Context Block

    Concatenate all resolved template entries into a single formatted block labeled "Candidate Email Templates". This block tells the AI what response patterns are available and when each should be used, without prescribing which to pick — that judgment is left to the LLM based on the full case context.

  5. 5

    Query Historical Closed Cases

    Query up to 3 recently closed Case records with the same Type and Reason, along with their associated outbound EmailMessage bodies. These are formatted as labeled few-shot examples and appended to the context block under "Historical Examples".

  6. 6

    Return {promptContext}

    The Flow outputs the fully assembled context string. This is bound to the {promptContext} input variable of the active GenAI Prompt Template (CSR First Contact Email or CSR Reply Email), which then generates the AI draft returned to the CSR.

Path Routing
The Agent Action determines Path A vs Path B before calling the Prompt Template. Path A invokes CSR First Contact Email; Path B invokes CSR Reply Email. Both receive the same {promptContext} from the Flow. The distinction controls prompt tone and whether the thread history is included in the context.

Why This Architecture

The revised design was chosen for the following reasons, each addressing a concrete problem with the original approach.

  • Single source of truth. Email body text lives in exactly one object (EmailTemplate.Body). Content editors use the native Setup UI or the Email Templates folder to make changes. There is no second record to update.
  • No sync drift. With the old design, a body updated in one location but not the other would cause the AI to receive stale or inconsistent content silently. The new design makes this physically impossible — the body is retrieved at runtime from the only place it exists.
  • Native Salesforce tooling. Classic Email Templates are a first-class Salesforce feature with version history, folder organization, rich text editing, and standard permission controls. Using them gives content teams familiar tooling rather than raw CMT field editing.
  • CMT is right-sized. Custom Metadata Types are designed for configuration and routing logic, not long-form content storage. Removing Template_Body__c returns the CMT to its intended purpose: a lightweight lookup table.
  • No Flow changes to add a template. Adding a new scenario requires only two record creations: an Email Template and a CMT record pointing to it. The Prompt Flow does not need to be modified, versioned, or redeployed.
  • Audience-appropriate access control. Admins manage routing logic (CMT). Content authors manage email bodies (Email Templates). Developers own the Flow and Prompt Templates. These responsibilities map cleanly to separate Salesforce permission boundaries.
  • Demo fidelity. The architecture reflects how a production Agentforce email assist deployment would be built in a real Salesforce org, making the demo credible as a blueprint — not just a proof of concept.

Extension Guide

Adding a new template scenario requires exactly two steps. No changes to the Prompt Flow, Agent Actions, or GenAI Prompt Templates are needed.

📄

Step 1 — Create the Email Template

Navigate to Setup → Email Templates → Allergan Demo Templates (Classic Email Templates). Create a new text template. Set a descriptive DeveloperName using underscores (e.g., Billing_Dispute_Initial_Response). Write the full email body in the Body field. Set a Subject. Save the record. Note the exact DeveloperName — you will need it in Step 2.

⚙️

Step 2 — Create the CMT Selection Record

Navigate to Setup → Custom Metadata Types → Template Scenario → Manage Records → New. Fill in the following fields:

• MasterLabel — human-readable name (e.g., Billing Dispute Initial Response)
• Case_Type__c — must match the Case.Type picklist value exactly
• Case_Reason__c — must match the Case.Reason picklist value exactly
• Email_Template_API_Name__c — the DeveloperName from Step 1
• When_To_Use__c — 1–3 sentences describing when the AI should choose this template
• Is_Active__c — check to enable routing to this template immediately

Save the record. The Prompt Flow will automatically include this template in its context block on the next agent invocation for a matching case — no deployment required.

Zero Downtime
CMT record saves deploy instantly in Salesforce (unlike Apex or Flow changes). New template scenarios are live the moment the CMT record is saved — no sandbox-to-production deployment cycle required for content additions.

To Deactivate a Template

Set Is_Active__c = false on the CMT record. The Prompt Flow will immediately stop resolving that template. The Email Template record is preserved for future reactivation or audit.

To Update Template Content

Edit the Body field of the Email Template record in Setup. No CMT changes needed. The updated body is resolved on the next Flow execution.
