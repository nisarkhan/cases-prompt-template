Architecture Walkthrough
How the system routes a case to the right email template - and drafts the response
End-to-end: CSR clicks "Draft with AI"
Follow each step from the case record to the generated email draft
Step 1 - Salesforce Case
CSR opens a case and clicks "Draft with AI"
The case already has a Case Type and Case Reason set by the CSR or intake process. These two fields are the routing keys - everything downstream depends on them.

Case Type Case Reason Email Thread (Activity)
Step 2 - GenAI Prompt Template (Agentforce)
CSR picks a template: "CSR First Contact Email" or "CSR Reply Email"
Two GenAI Prompt Templates are available. The CSR picks one based on whether this is a new enquiry or an ongoing thread.

Custom_CSR_Response First Contact  ·  Custom_CSR_Reply Reply

Each template calls the same Prompt Flow to inject the relevant template context before the AI writes the draft.
Prompt Flow invoked
Step 3 - Prompt Flow
Add Historical Case Emails to Prompt2
The flow reads the Case fields and does two things in parallel:

1. Fetches the email history - loops the Activity timeline and appends prior emails to the prompt so the AI has full context.

2. Finds candidate templates - queries Template_Scenario__mdt where Case Type and Case Reason match. For each match, it reads the Email_Template_API_Name__c pointer and fetches the body from EmailTemplate. The template name, when-to-use guidance, and body are all appended to the prompt.
CMT lookup
Step 4 - Custom Metadata Type (Routing Index)
Template_Scenario__mdt - matches Case Type + Reason to a template pointer
Each CMT record is a routing rule. The flow queries: WHERE Case_Type__c = [case type] AND Case_Reason__c = [case reason]

What it returns: one or more records, each with:
 · MasterLabel - human-readable template name
 · When_To_Use__c - guidance text for the AI on when to pick this template
 · Email_Template_API_Name__c - the pointer to the actual EmailTemplate

8 records covering credentialing + patient support scenarios.
EmailTemplate lookup by DeveloperName
Step 5 - EmailTemplate (Body Source)
Flow fetches body: EmailTemplate WHERE DeveloperName = [pointer]
The EmailTemplate Body field holds the full template text - form references, SLA numbers, compliance language, policy statements.

Why here? Content teams edit template language in Setup → Email Templates, a familiar UI. They never touch CMT or Flow metadata.

10 EmailTemplates in the Allergan Demo Templates folder - 6 credentialing + 4 patient journey.
All context assembled → sent to AI
Step 6 - Einstein AI (LLM)
AI selects the best template and writes the personalised draft
The AI receives a prompt containing:
 · Case description and details
 · Prior email thread (from Activity)
 · All candidate templates with their when-to-use guidance and full body text

It selects the most relevant template, uses its body as the structural backbone, and personalises the draft using case-specific details (names, dates, product lots).
Step 7 - Output
Draft appears in the Email composer. CSR reviews and sends.
The draft is pre-populated in the Salesforce Email composer. The CSR can edit, revise, or regenerate before sending. The selected template name appears at the top of the draft so the CSR knows which template drove the output.
Component Inventory
What each piece is, where it lives, and who owns it
Salesforce Platform
Case Record

What it is: A standard Salesforce Service Cloud Case. Holds the customer inquiry, contact, and email Activity thread.

Key fields used: Type (Case Type) and Reason (Case Reason) - the two routing keys that determine which templates are returned.

Who owns it: Allergan Moxie team - CSRs create and manage cases.

Agentforce / Einstein GenAI
GenAI Prompt Templates

What it is: Two Salesforce GenAI Prompt Templates configured in the org. These are the entry points - the CSR picks one from the Draft with AI menu.

Records:
Custom_CSR_Response - "CSR First Contact Email"
Custom_CSR_Reply - "CSR Reply Email"

Who owns it: Salesforce admin / SA. Each template calls the Prompt Flow to assemble context.

Salesforce Flow (PromptFlow type)
Prompt Flow

What it is: A Flow of type PromptFlow. It assembles the full AI prompt - email history + template candidates + template bodies.

Record: Add_Historical_Case_Emails_to_Prompt2

Key nodes:
Get_Candidate_Templates → CMT query
Get_Email_Template_Body → EmailTemplate lookup
Append_Template_Entry → builds the prompt string

Who owns it: Salesforce admin / SA. Do not edit without testing.

Custom Metadata Type
Template Scenario (Routing Index)

What it is: Template_Scenario__mdt - a Custom Metadata Type where each record maps a Case Type + Reason combination to a template pointer.

Key fields:
Case_Type__c · Case_Reason__c - routing keys
Email_Template_API_Name__c - pointer to EmailTemplate
When_To_Use__c - guidance text passed to the AI

Who owns it: Salesforce admin. Allergan team can add new routing rules here when new scenarios are needed.

Salesforce Email Templates
EmailTemplate (Body Source)

What it is: Native Salesforce Email Templates, stored in the Allergan Demo Templates folder. Each template's Body field holds the full template text.

10 templates deployed: 6 credentialing + 4 patient journey. Each has a unique DeveloperName that the CMT record points to.

Who owns it: Content team / Allergan. Template language is edited here - no code changes needed to update an email template.

Einstein AI / LLM
Draft Generation

What it is: The Einstein LLM that receives the fully assembled prompt and generates the personalised email draft.

What it receives: case fields, email thread, candidate templates with when-to-use guidance, and the full template body text for each candidate.

What it does: Selects the best-fit template based on the when-to-use guidance, uses the template body as structure, and personalises using case-specific details.

Before vs After
What changed when we moved the template body out of CMT and into EmailTemplate
Before - Template body stored in CMT
Where the body lived Template_Body__c field on each CMT record - a long text area baked into the metadata object.
How to update template language Go to Setup → Custom Metadata Types → Template Scenario → manage records. Edit the Template Body field (a textarea, no formatting). Deploy if in a sandbox. Not intuitive for a content team.
Who can edit it Salesforce admin or SA only - requires metadata deployment access in most orgs. Content teams cannot edit CMT records in production without a release.
Flow behaviour Flow read {!CurrentTemplate.Template_Body__c} directly - simple, but body was frozen in deployed metadata.
Adding a new scenario Create a CMT record, paste the entire body into Template_Body__c, deploy. Two steps, one tool.
After - Template body stored in EmailTemplate
Where the body lives EmailTemplate.Body - native Salesforce Email Templates in the Allergan Demo Templates folder.
How to update template language Setup → Email Templates → Allergan Demo Templates → open template → edit body. Familiar UI, rich text supported, no deployment required. Content teams can own this.
Who can edit it Any Salesforce user with the Manage Public Classic Email Templates permission - no metadata deployment access needed for edits.
Flow behaviour Flow reads Email_Template_API_Name__c from CMT, then does a live lookup: EmailTemplate WHERE DeveloperName = [pointer]. Body is always the current live version.
Adding a new scenario Create EmailTemplate (folder: Allergan Demo Templates) → create CMT record pointing to it → optionally deploy CMT record. Two tools, cleaner ownership split.
What stayed exactly the same for the CSR

The CSR experience is identical. Same "Draft with AI" button. Same template names in the dropdown. Same draft quality. Same ability to revise or regenerate. The change is entirely under the hood - the CSR never sees CMT fields or EmailTemplate DeveloperNames. The only observable difference is that when Allergan's content team updates template language, the next draft generation reflects the change immediately - no waiting for a deployment.
